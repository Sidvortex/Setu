# 10. Security

What protects Setu today, what doesn't, and the rules for handling secrets.

## Officer logins

- **No public sign-up.** Accounts are created only with
  `backend/create_admin.py`, by someone with database access.
- **Passwords** are hashed with **bcrypt** (a random salt per password); the
  plain password is never stored. `create_admin.py` asks for it without
  showing it and requires at least 10 characters.
- **Sessions** are JWTs signed with `AUTH_SECRET` (HS256), valid for **12
  hours**. The backend checks the token on every official endpoint
  (`Depends(auth.require_auth)`); hiding a page in the browser is not the
  protection.
- **One role:** every account is an `authority`. There are no finer
  permissions yet.

Gaps:

- No limit on failed login attempts (no lockout or delay).
- No two-factor login.
- Tokens are kept in the browser's `localStorage`, readable by any script
  running on the page; a cross-site-scripting bug would expose them. Logging
  out removes the token locally but cannot revoke it on the server before it
  expires. Rotating `AUTH_SECRET` logs everyone out at once.

## Secrets

| Secret | Where it lives | Never |
|---|---|---|
| `AUTH_SECRET` | Render (generated by the Blueprint) | In git, in chat, reused between Setu and BhooSuraksha |
| `TURSO_AUTH_TOKEN` | Render; your terminal only when creating accounts | In git, in chat, in screenshots |
| `GEMINI_API_KEY` / `ANTHROPIC_API_KEY` | Render | In the frontend (it would be public) |
| Officer passwords | The person's head or password manager | Typed into a visible command or chat |

Rules:

- `.env` files and `*.db` files are git-ignored. Check `git status` before
  committing.
- Use `read -rs TURSO_AUTH_TOKEN && export TURSO_AUTH_TOKEN` (or PowerShell's
  `Read-Host -MaskInput`) so tokens don't land in shell history.
- If a token or password was shown anywhere (a chat, a log, a screenshot),
  replace it: invalidate Turso tokens and create new ones, reset passwords with
  `create_admin.py <username> --reset`, and clear shell history
  (`history -c`).
- Logs can contain tokens when a connection error prints its headers. Remove
  those lines before sharing logs.

## Production safety checks

With `SETU_ENV=production` (set in `render.yaml`), the backend **refuses to
start** if `AUTH_SECRET` is the development default or shorter than 32
characters, and warns in the log if `ALLOWED_ORIGINS` is `*`.

## CORS

`ALLOWED_ORIGINS` lists the websites whose pages a browser will let call the
API. With `*`, any website's pages can. With the Setu site's address, only
that site can.

What it **does** protect: other websites can't use their visitors' browsers to
call Setu's API (for example to display its data as their own, or to send
reports from their visitors' browsers and use up free hosting hours).

What it **doesn't** protect: CORS is enforced by browsers only. Scripts,
`curl` and Postman ignore it, so it is not access control. Access control is
the login on official endpoints and the rate limit on public reports.

Setu's backend calling BhooSuraksha is server-to-server, so BhooSuraksha's
`ALLOWED_ORIGINS` never blocks it.

## Public reports

- **Rate limit:** 5 reports per hour per connection, checked in the database
  (HTTP 429 after that).
- **IP privacy:** raw IP addresses are never stored. The backend stores
  `sha256(AUTH_SECRET + "|" + ip)`, cut to 32 hex characters, only to count
  reports per connection.
- **Weakness:** the IP is taken from the first entry of the
  `X-Forwarded-For` header, which a client can set itself, so a determined
  sender can get around the limit. A fix is to use the address added by
  Render's proxy instead of the first one (see [Roadmap](12-roadmap.md)).
- **No automatic action:** a public report never changes road status by
  itself. An official must verify it.
- **The credibility score is hidden from reporters,** so they can't tune a fake
  report to pass. Officials see the score and every reason.
- **Duplicates** with the same `client_id` return the first report instead of
  creating a new one.

## Uploaded photos

- Only JPEG and PNG are accepted, checked by the file's first bytes (not its
  name), up to 3 MB.
- Each photo gets a random 32-character hex name. The download endpoint only
  accepts names in exactly that form, which blocks path tricks like `../`.
- Photo addresses are **public to anyone who has the link** (the review page
  shows them to officials). The names can't be guessed, but anyone a link is
  shared with can see the photo.
- Photos are sent to Google or Anthropic only if the AI photo check is turned
  on.

## Driver tracking links

- Each shipment's link contains a random token (`secrets.token_urlsafe(16)`,
  about 128 bits), so links can't be guessed.
- Anyone with the link can see that shipment's commodity, destination and ETA,
  and send positions for it, until it is delivered or cancelled (then pings
  get HTTP 409).
- Share links only with the driver, over a private channel.

## Input validation

Every request body is validated by pydantic: allowed values for reasons,
types, severities, commodities, units and priorities; text length limits;
coordinates limited to the North East box (latitude 20–30.5, longitude
87.5–97.5); `client_id` 8–64 characters. Invalid input gets HTTP 422 before
any code runs. Every value in SQL goes through parameter placeholders (`?`);
the only text joined into SQL strings is fixed column names from the code.

## Personal data held

| Data | Why | Who sees it |
|---|---|---|
| Officer usernames | Login, "reported by", "reviewed by" | Officials |
| Optional contact on public reports | So an official can follow up | Officials |
| Driver name, vehicle registration, last position | Shipment tracking | Officials; the driver (own shipment) |
| Hashed IP of public reporters | Rate limit | Nobody (not reversible without the secret) |

There is no automatic deletion yet. For a real launch, decide how long
reports, photos and positions are kept, and publish a privacy notice.

## Dependencies

Python packages are pinned to exact versions (`requirements.txt`) and npm
packages are locked (`package-lock.json`), so a deploy never pulls an
untested version. Update them deliberately, then run the tests.
