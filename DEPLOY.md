# Deploying Setu and BhooSuraksha (free plans)

Where each part goes:

| Part | Host | Plan | Address you'll get |
|---|---|---|---|
| BhooSuraksha backend | Render | Free | `https://bhoosuraksha-api.onrender.com` (or similar) |
| Setu backend | Render | Free | `https://setu-api.onrender.com` (or similar) |
| BhooSuraksha website | Vercel | Hobby (free) | `https://<name>.vercel.app` |
| Setu website | Vercel | Hobby (free) | `https://<name>.vercel.app` |
| Databases (logins, road status, reports, photos) | Turso | Free | `libsql://...turso.io` |

No credit card and no command-line tools are needed except Python and git on
your own computer (for creating officer accounts).

**Never paste passwords, tokens or secrets into chat, issues or commits.**
They go only into the Render / Vercel environment-variable screens, or into
your own terminal.

---

## What "free" means here

- A free Render backend **sleeps after 15 minutes with no visitors**. The next
  visitor waits about a minute while it starts. Both websites ping their
  backend as soon as a page opens and show *"Waking up the server…"* until it
  answers; data then loads by itself. Setu's backend also wakes BhooSuraksha's
  when it starts.
- Free Render gives **750 hours a month per workspace** in total. Two services
  that sleep when idle stay well under that. Don't add an uptime pinger that
  keeps them awake 24/7: two always-on services would need 1,440 hours.
- A free Render server's **disk is wiped** whenever it sleeps or redeploys.
  That's why everything that must be kept (accounts, road status, reports,
  photos) goes in Turso.
- Before a demo or judging round, open both websites ~2 minutes early so the
  servers are awake.

## Step 1 — Accounts

Sign up (GitHub login works for all three):

1. **Render** — https://render.com
2. **Vercel** — https://vercel.com
3. **Turso** — https://turso.tech

When Render and Vercel ask for GitHub access, allow access to the
`Sidvortex/Setu` and `Sidvortex/BhooSuraksha` repositories.

## Step 2 — Two Turso databases (one per project)

In the Turso dashboard (https://app.turso.tech):

1. **Create Database** → name `setu` → pick the location closest to India
   (e.g. Mumbai if listed, otherwise Singapore).
2. Create another one named `bhoosuraksha`.
3. For each database, note two things (keep them in a password manager, not
   in a file in the repo):
   - the **URL** (`libsql://setu-<you>.turso.io`)
   - a **token**: database page → *Create Token* (read & write, no expiry).

## Step 3 — BhooSuraksha backend on Render

1. Render dashboard → **New → Blueprint** → choose `Sidvortex/BhooSuraksha`.
   Render reads `render.yaml` from the repo and shows one service,
   `bhoosuraksha-api`, on the Free plan.
2. It asks for the values marked `sync: false`:
   - `TURSO_DATABASE_URL` → the **bhoosuraksha** database URL
   - `TURSO_AUTH_TOKEN` → the **bhoosuraksha** token
   - `ALLOWED_ORIGINS` → `*` for now (locked down in Step 8)
   `AUTH_SECRET` is generated by Render automatically — nobody needs to see it.
3. **Apply**. The first build takes a few minutes.
4. Check it: open `https://<bhoosuraksha-api address>/health` → `{"status":"ok"}`,
   and `/api/models` → lists `ner`, `india`, `region`.

## Step 4 — Setu backend on Render

1. **New → Blueprint** → choose `Sidvortex/Setu`. It shows `setu-api`.
2. Fill in:
   - `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN` → the **setu** database's values
   - `BHOOSURAKSHA_API_URL` → BhooSuraksha's address from Step 3, **no trailing
     slash**, e.g. `https://bhoosuraksha-api.onrender.com`
   - `ALLOWED_ORIGINS` → `*` for now
   `AUTH_SECRET` (a different one from BhooSuraksha's) and `SETU_ENV=production`
   are set by `render.yaml`.
3. **Apply**, then check `https://<setu-api address>/ready`. You want
   `"database":"ok"`, `"road_network":"ok (...)"`, and under `bhoosuraksha`
   `"configured": true`. (`last_ok` turns `true` once BhooSuraksha has
   answered; give a sleeping BhooSuraksha a minute.)

## Step 5 — Officer accounts

Render's free plan has no shell, so create accounts **from your own computer**,
pointed at the Turso database. In a terminal, inside the repo's `backend/`
folder (with `pip install -r requirements.txt` done once):

macOS / Linux:
```bash
export TURSO_DATABASE_URL="libsql://setu-<you>.turso.io"
export TURSO_AUTH_TOKEN="<paste the setu token here, in your terminal only>"
python create_admin.py <username> <password>
```

Windows PowerShell:
```powershell
$env:TURSO_DATABASE_URL="libsql://setu-<you>.turso.io"
$env:TURSO_AUTH_TOKEN="<paste the setu token here, in your terminal only>"
python create_admin.py <username> <password>
```

Do the same in BhooSuraksha's `backend/` with the **bhoosuraksha** URL and
token. Use a different strong password for each person; there is no public
sign-up page by design.

## Step 6 — Websites on Vercel

For each project: Vercel → **Add New → Project** → import the repo, then:

| Setting | BhooSuraksha | Setu |
|---|---|---|
| Root Directory | `frontend` | `frontend` |
| Framework | Vite (detected) | Vite (detected) |
| Environment variable | `VITE_BACKEND_URL` = BhooSuraksha backend address | `VITE_BACKEND_URL` = Setu backend address |

No trailing slash on the addresses. `frontend/vercel.json` already sets the
build and makes direct links like `/track/<token>` work.

`VITE_BACKEND_URL` is built into the site, so **if you change it, redeploy**
(Deployments → ⋯ → Redeploy).

## Step 7 — Check everything

- [ ] Open the Setu site. If the backend was asleep you'll see *"Waking up the
      server…"*, then *"Connected."*, and the road map loads.
- [ ] Officials Login works with an account from Step 5.
- [ ] Block a road in Ops → it appears in the public Road Alerts ticker.
- [ ] Report a problem from a phone (needs https, which Vercel gives you), with
      a photo. In Ops → Incidents the photo shows.
- [ ] Create a shipment, open its driver link on a phone, allow location.
- [ ] Open the BhooSuraksha site: the zones show real model scores (not the
      sample data), and its authority login works.

## Step 8 — Lock down

Now that the website addresses exist, set `ALLOWED_ORIGINS` on each Render
service (Service → Environment) to its own website, comma-separated if more
than one:

- `setu-api` → `https://<setu-site>.vercel.app`
- `bhoosuraksha-api` → `https://<bhoosuraksha-site>.vercel.app`

Saving restarts the service. Setu's backend talks to BhooSuraksha
server-to-server, so it isn't affected by BhooSuraksha's `ALLOWED_ORIGINS`.

Optional — AI photo check on public reports (Setu): add `AI_PROVIDER`
(`gemini` or `anthropic`) and the matching `GEMINI_API_KEY` or
`ANTHROPIC_API_KEY` on `setu-api`. Without them the rule-based credibility
score still works.

## Troubleshooting

| Symptom | Cause / fix |
|---|---|
| Render deploy fails with "AUTH_SECRET must be set…" | The secret is missing or short. In render.yaml it's generated; if you created the service by hand, add `AUTH_SECRET` (any 64 random characters). |
| "Incorrect username or password" on the live site | The account was created in a different database. Redo Step 5 with the deployed database's URL and token. |
| Site loads but all data fails, browser console says CORS | `ALLOWED_ORIGINS` doesn't exactly match the site address (https, no trailing slash). |
| BhooSuraksha site shows sample data | `VITE_BACKEND_URL` wasn't set before the build — set it and redeploy. |
| `/ready` shows `bhoosuraksha.last_error` | BhooSuraksha was asleep or the URL is wrong. Open its `/health`; Setu retries automatically after 2 minutes. |
| "Can't reach the server right now" after 90 s | The backend failed to start — check the service's Logs on Render. |
| Render says the free hours are used up | Something is keeping the services awake (e.g. an uptime pinger). Remove it; hours reset monthly. |
